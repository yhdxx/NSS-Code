# 制定代码计划

## 适用条件

简单、局部且实现路径明确的修改不必形式化列计划。出现跨模块依赖、多个可行方案、不可逆数据变化、外部接口变化或需求歧义时，必须先规划。

## 工作流

1. 确认已具备足够项目事实；证据不足时先调用并遵循 `project-reading`。
2. 明确目标、范围、不处理的内容、约束、假设和可观察的完成条件。
3. 描述当前行为及证据，标出受影响的模块、接口、状态、数据流、权限和持久化边界。
4. 解决会改变实现方向的关键未知项。属于产品或权限选择的问题交给用户，不用技术假设代替决定。
5. 按依赖顺序拆分实施步骤。每一步写清修改位置、行为变化、与前后步骤的关系及完成判据，确保实施者不必重新设计。
6. 根据风险列出失败处理、恢复或回滚策略，以及单元、集成、协议、持久化或界面验证范围。
7. 给出可执行的验证命令、验收标准和仍然存在的非阻塞问题。

## 质量标准

- 计划基于已读源码，不把探索动作伪装成实施步骤。
- 优先最小且完整的修改，不加入无依据的兼容层、抽象或无关重构。
- 测试策略覆盖行为风险和回归面，不要求与风险无关的全量测试。
- 若使用 Plan Runtime，只在计划已经决策完整时调用 `create_plan`；该调用必须是本轮唯一工具调用，随后等待用户选择。
