# 实施代码修改

## 开始前

1. 确认用户授权的是实现而非仅调查、解释或审查。
2. 确认相关源码、仓库约定和计划仍与工作区一致；上下文不足或可能过期时先调用并遵循 `project-reading`。
3. 复杂变更没有可执行计划时调用并遵循 `code-plan`。执行已批准计划时不得擅自改写目标和步骤。

## 实施循环

1. 选择最小的连贯行为单元，明确预期结果和本轮验证方式。
2. 行为新增、缺陷修复或重构需要测试先行时，调用并遵循 `test-driven-development`；选择最接近行为契约的测试层级。
3. 按仓库现有模式编辑拥有该行为的模块。保持接口、错误处理、状态更新和调用方同步，不做无关整理。
4. 运行聚焦验证并检查实际输出。失败时先诊断原因；复杂或反复失败时调用并遵循 `systematic-debugging`。
5. 检查差异是否遗漏调用方、配置、文档或测试，并确认没有意外修改用户已有工作。
6. 执行 Plan Runtime 计划时，在步骤开始、完成或真正阻塞时更新对应状态，再进入下一步。

## 完成门槛

- 不越过用户边界，不自行提交、推送、发布或执行难以恢复的外部操作。
- 不为未知消费者添加兼容逻辑；确有兼容要求时说明依据并覆盖测试。
- 完成前调用并遵循 `verification-before-completion`，用最新验证结果支撑结论。
- 最终说明修改结果、关键文件、执行过的验证及仍未验证的风险；没有证据时不得声称完成或测试通过。
